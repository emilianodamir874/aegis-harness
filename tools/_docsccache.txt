

## sccache ROTO Y REPARADO (12/10, 20:5x)

**Sintoma**: toda compilacion Rust fallaba con
```
sccache: error: failed to execute compile
sccache: caused by: Failed to send data to or receive data from server
sccache: caused by: Failed to read response header
sccache: caused by: failed to fill whole buffer
```
mientras `sccache --show-stats` seguia respondiendo (por eso despistaba).

**Causa raiz**: el *servidor* sccache arrastraba `Cache location Local disk: "/home/emiliano/.cache/sccache"`
— una **ruta Linux** que en Windows no existe. El cliente no podia completar los pedidos de
compilacion, pero las estadisticas (otro endpoint) si funcionaban. No habia config de sccache en
ninguna ubicacion estandar ni `SCCACHE_DIR` en el entorno: era un server viejo con un entorno malo.

**Fix aplicado**:
1. `SCCACHE_DIR=C:\Users\Emiliano\AppData\Local\sccache` fijado como **variable de usuario**
   (persistente: lo heredan todas las terminales nuevas).
2. `sccache --stop-server` + `taskkill` para bajar el server contaminado; el siguiente build
   levanta uno nuevo que ya lee la ruta correcta.

**Verificado con compilaciones reales** (target dir limpio, arbol de dependencias entero):
```
Finished `dev` profile in 47.90s
Compile requests executed  137
Cache hits rate            0.00 %   (cache nueva -> compila de verdad, no es un no-op)
Cache write errors            0
Cache errors                  0
Cache location  Local disk: "C:\Users\Emiliano\AppData\Local\sccache"
```

**Nota para el futuro**: si sccache vuelve a fallar, chequear primero `sccache --show-stats | findstr
"Cache location"`. Si no es una ruta Windows, la variable de usuario `SCCACHE_DIR` se perdio.
Metodo alternativo (el que se uso para construir v3 mientras estaba roto): comentar
`rustc-wrapper` en `~/.cargo/config.toml` dentro de un try/finally que siempre lo restaura
(`C:\goose-web\tools\build-v3.ps1`).

## Resultado MEDIDO del fix del reload en v3 (importante: NO alcanza)

Con v3 (build 20:41, que incluye el cambio del `Drop` del guard) se repitio el test
(`ui/desktop/scripts/goose-web-reload-v3.mjs`, con el puerto del WebSocket reescrito a 3391 para
pegarle a v3 sin tocar el serve desplegado).

| | v2 (desplegado) | v3 (con el Drop sin cancel) | esperado con el fix completo |
|---|---|---|---|
| persistido tras el reload | corta en `thinking` | **avanza hasta el `toolRequest`** | `toolResponse` + respuesta final |

Es decir: **el cambio del `Drop` mejora un paso pero no cura el bug**. Motivo: al cerrarse la
conexion no solo se dropea el guard, se dropea **el futuro entero de `on_prompt`**, y con el el
`forward_agent_stream` que esta esperando el resultado de la herramienta. Quitar el `cancel()`
evita la cancelacion explicita, pero no resucita un futuro que ya no existe.

### Fix que falta (diseno, con el bloqueante identificado)

Hay que **desacoplar el run de la conexion**: ejecutar desde `let stream = agent.reply(...)`
(server.rs:2408) hasta el armado del `PromptResponse` (2461) dentro de un `tokio::spawn`, y que
`on_prompt` espere el `JoinHandle`. El `cancel_token` ya es explicito, asi que `Detener` seguiria
funcionando; el watchdog tambien.

**Bloqueante tecnico**: los handlers reciben `&self` (`async fn on_prompt(&self, ...)`,
server.rs:2337, dentro del `impl GooseAcpAgent` de la linea 1865), y para un `spawn` hace falta un
`Arc<GooseAcpAgent>` o equivalent. El `Arc` existe (el runner lo tiene: server.rs:2743
`pub agent: Arc<GooseAcpAgent>`) pero no es alcanzable desde `&self`. Opciones:
1. cambiar el trait/impl del handler para que sea sobre `Arc<GooseAcpAgent>` (asi `self.clone()` da
   el `Arc`) — probablemente via la macro de `goose-acp-macros`;
2. o extraer el tramo a una funcion libre que reciba solo los `Arc` que necesita
   (`active_runs`, `agent`, `cx`) en vez de `&self`, moviendo dentro las llamadas a
   `forward_agent_stream` / `clear_active_run` / `send_session_usage_updates`.

La opcion 2 es mas contenida y no toca el codigo generado por la macro. **No se hizo** por riesgo:
es el camino critico de TODOS los prompts y un error de concurrencia ahi rompe el producto; requiere
una sesion de trabajo propia con el test de recarga como red de seguridad.
