# v6.4 — Sesión = unidad de streaming (fan-out por sesión + run desacoplado)

Estado: EN IMPLEMENTACIÓN (2026-10-12 21:45 -03:00). Reemplaza al doc v6.3 en lo que contradiga.

## Problema medido (evidencia)

1. `AcpServer::create_agent()` se llama **por conexión** (`AegisAgentConnection::connect_to`,
   `crates/aegis/src/acp/server.rs:2790`). `AegisAcpAgent::new` (línea 1026) arma **por conexión**:
   `SessionManager::new` (pool SQLite propio), `AgentManager::new(agent_config, None)` (LRU de 100
   agentes propio), `sessions: HashMap` propio, `permission_manager`, `provider_inventory`.
   Solo `active_runs` y `live_voice` se comparten (`server_factory.rs:42`).
   ⇒ Dos conexiones sobre la misma sesión tienen **dos `Arc<Agent>` distintos**, historiales en
   memoria divergentes y escritura concurrente sobre la misma fila SQLite.

2. Los `session/update` del turno salen con `cx` = **la conexión que llamó `session/prompt`**
   (`forward_agent_stream`, `server.rs:2197+`). El transporte
   (`agent-client-protocol-http 2.2.0`, crate de crates.io) **no tiene fan-out**: un mailbox = un
   suscriptor activo (`sse_allows_one_active_subscriber_per_logical_stream`; `handle_get` devuelve
   **409 CONFLICT** si ya hay suscriptor). ⇒ Ninguna otra pestaña/celular ve el mismo streaming.

3. Al cerrarse el WS el transporte hace `registry.remove()` + `connection.shutdown()`
   (`websocket_server.rs:74-76`) → `abort()` de la task del agente → **se dropea el futuro de
   `on_prompt`** → se corta el consumo del stream. Medido y documentado: la conversación persistida
   queda cortada en el bloque de thinking, sin toolRequest ni respuesta
   (`docs/v6.3-serve-v3.md`, "el fix del Drop NO alcanza").

4. `ActiveRunDropGuard::drop` (server.rs:250-278) ya no cancela el token, pero **sí**
   `remove_agent_run` + `discard_pending_steers`. Si el run sigue vivo dentro del agente, la sesión
   queda "libre" con un run corriendo ⇒ se puede arrancar un **segundo run concurrente** sobre la
   misma sesión y se tiran los steers encolados.

5. Ruido: el cliente sondea el run con `_aegis/unstable/session/steer` + `expectedRunId` falso
   (`app/app.js:1733`) cada 2,5 s ⇒ **2505 líneas ERROR "no active run to steer" en 5 h** de serve.

6. Externo (no lo arregla este doc): el proveedor devolvió 60 × HTTP 503
   `workspace_billing_scope_unavailable` (amr-link.open-design.ai) en ráfagas 16:20–17:10 y
   20:10–20:20. Con el fan-out + watchdog, esos fallos se ven y la sesión se recupera sola.

## Objetivo

- Una sesión = **un** `Arc<Agent>` compartido por todas las conexiones.
- Un turno = **un** run, desacoplado de la conexión que lo arrancó, observable en vivo por
  **todas** las conexiones suscriptas, y sobreviviente a reload/cierre de pestaña.
- Que el que entra tarde o recarga **vea el mismo streaming** (replay por cursor desde el hub).

## Contrato (protocolo nuevo, server → cliente)

Todo viaja por `cx` de cada conexión: el hub guarda **canales**, no `ConnectionTo<Client>` de otras
conexiones (evita leaks y ciclos).

### Método `_aegis/unstable/session/watch`

```jsonc
// request
{ "sessionId": "<id>", "since": null | <cursor:u64> }   // since: null = desde ahora + snapshot de estado
// response
{ "activeRunId": "run_..." | null, "cursor": 42, "replay": [ /* notificaciones JSON-RPC completas */ ] }
```

- Registra la conexión emisora como watcher de `sessionId` (idempotente; re-watch reemplaza).
- `replay`: los eventos que un watcher nuevo (o reconectado con `since`) necesita para quedar al día:
  todas las notificaciones `session/update` / `_aegis/unstable/session/update` desde `since`
  (o desde el inicio del run si `since` es null), en orden, incluyendo el último
  `_aegis/unstable/session/update` con `aegis.activeRunId`.
- `replay` está acotado: ring buffer por sesión, máximo 2 MB o 500 eventos; si se truncó, el primer
  elemento es `{"method":"_aegis/unstable/session/replay_gap","params":{"sessionId":...}}` y el
  cliente debe hacer `session/load` completo.

### Notificaciones que el hub emite a **todos** los watchers de la sesión

- `session/update` (los actuales, sin cambios de forma: el cliente ya los sabe renderizar).
- `_aegis/unstable/session/update` con `params.aegis.activeRunId` ∈ {`"run_..."`, `null`}:
  al arrancar el run, y **también al terminar** (aunque muera la conexión dueña).
- `_aegis/unstable/session/info` incluye `session._meta.activeRunId` (deja de necesitarse el sondeo
  por steer).

### Método `_aegis/unstable/session/unwatch`

`{ "sessionId": ... }` → desregistra. También se desregistra solo cuando muere la conexión.

### Compatibilidad

Si el server no implementa `watch` (v2/v3), el cliente cae al comportamiento viejo (soft-poll).
El server v4 debe seguir aceptando todos los métodos viejos sin cambios.

## Diseño server (crate aegis)

1. **Un stack por sesión** (`server_factory.rs` + `server.rs`): `AcpServer` guarda
   `agent_manager: OnceCell<Arc<AgentManager>>` y `session_manager: OnceCell<Arc<SessionManager>>`
   creados una sola vez; `create_agent()` los reusa (el `AgentManager` debe quedar con capacidad
   de `AEGIS_MAX_ACTIVE_AGENTS`, no `None`). Resultado: la misma sesión → el mismo `Arc<Agent>`.
2. **`SessionHub`** en `AcpServer`:
   - `watchers: Mutex<HashMap<String /*session*/, HashMap<u64 /*watcher*/, mpsc::UnboundedSender<String /*json*/>>>>`
   - `log: Mutex<HashMap<String, RingBuffer<(u64 /*cursor*/, String /*json*/)>>>`, caps 500 eventos / 2 MB.
   - `publish(session_id, json)`: asigna cursor, empuja al ring, reenvía a todos los watchers
     (si un `send` falla, se poda). Nunca bloquea el stream del agente.
   - Los watchers se registran con un **forwarder task** que vive en la conexión dueña:
     `hub.watch(session_id, cx.clone())` spawnea `while let Some(json) = rx.recv() { cx.send_raw(json) }`.
     Al morir la conexión muere el receptor → poda automática.
3. **Emisión por hub**: en `forward_agent_stream` (y en todo lugar que hoy hace
   `cx.send_notification(...)` para eventos de sesión: updates, usage, tool notifications, chain
   summaries, steering, permisos), serializar la notificación y publicarla en el hub; además,
   si la conexión emisora no es watcher, nada más (el hub ya la alcanza si es watcher).
   `ToolCallNotifier` y `spawn_ready_chain_summary` deben publicar por hub.
4. **Run desacoplado** (`on_prompt`): el cuerpo del turno se mueve a una `tokio::spawn` que
   (a) resuelve agente, (b) registra el run, (c) consume el stream, (d) publica
   `activeRunId=null` y limpia el registry, (e) persiste. El handler hace `handle.await`.
   En abort del transporte se dropea solo el `await`, **no la task**: el turno sigue, persiste y
   el hub avisa el fin a todos los watchers. El `ActiveRunDropGuard` se mueve **dentro de esa task**
   (así un abort de conexión no libera un run vivo) y `discard_pending_steers` se llama **solo** al
   terminar el run o en cancel explícito.
5. **Sin duplicación**: mientras un run está registrado, `session/prompt` de otra conexión sigue
   devolviendo "session already has active run" (comportamiento actual, correcto); la única vía de
   escritura en un turno vivo es `steer`.
6. Mantener el watchdog de stall de v3, apuntando a `cx` de los watchers (no a la conexión dueña).

## Cambios cliente (app/server.js)

1. Al renderizar una sesión (`session/load` + render), llamar `watch {sessionId, since: cursor}` y
   guardar `cursor`; aplicar `replay` con los mismos handlers que un evento vivo.
2. Con `watch` OK: **eliminar** el soft-poll de 15 s (`softResync`) y el sondeo por `steer`
   (`activeRunId()`), y el orphan watch; el fin de turno llega como evento `activeRunId=null`.
3. Al reconectar el WS: re-`watch` con el último `cursor`; si el server dice `replay_gap`,
   hacer `session/load` completo.
4. `session/prompt` sigue esperando su response para "fin de turno" del dueño, pero un
   `activeRunId=null` recibido por evento cierra el turno aunque el response se pierda (reload).
5. Guardar el comportamiento viejo detrás de detección de capacidad (`watch` ausente ⇒ fallback).
   Nunca dejar la consola muda: si a los N s no hay run y hay prompt sin respuesta, liberar
   (el actual orphan watch puede quedar como red de seguridad, sin los 2505 errores).

### Qué se implementó (requisito → código)

1. **Watch por sesión**: `watchSession()` (`app.js:1887`), llamado tras el `session/load` +
   render (`openSession`) y también en `newSession` (`startHubWatch()`, `app.js:2005`).
   Guarda `state.hubCursor` y aplica `replay[]` con `handleServerMessage` — los MISMOS
   handlers que un evento vivo, en orden — vía `hubApplyReplay()` (`app.js:1867`). Para no
   duplicar lo que ya trajo el `session/load`, los chunks de texto del replay se reconcilian
   por prefijo común (`hubApplyReplayText`, `app.js:1802`), las burbujas ya pintadas se
   descartan por messageId y el eco del propio prompt se fusiona en la burbuja local
   (`adoptLocalEcho`, `app.js:1853`).
   **Capacidad**: `-32601`/"Method not found" o una respuesta sin `cursor` ⇒ `state.hubWatch=false`
   y el camino viejo no cambia en nada.
2. **Con `hubWatch=true`**: (a) `softResync` retorna antes (`app.js:1003`) ⇒ soft-poll de 15 s
   apagado; (b) `activeRunId()` responde con `session/info` (`runIdFromInfo`) y nunca con
   `steer` (`app.js:2043`); (c) `startRunWatch` es no-op (`app.js:2098`) ⇒ no hay poll de 2,5 s;
   (d) reconexión: `hubRewatch()` (`app.js:1993`) re-watch con el último cursor y, ante
   `replay_gap` (o cursor que retrocede = ring liberado por TTL), `hubFullResync()` hace
   `session/load` completo + re-watch `since=null` conservando barra, cronómetro y steers;
   (e) `watcherCount`/`activeRunId` de `session/info._meta` son hint de UI
   (`updateMetaHints`, `app.js:1608`: "N conexiones sobre esta sesión").
3. **Fin de turno por evento**: `applyActiveRunId()` (`app.js:2035`) cierra el turno tanto si
   somos dueños del prompt como si lo adoptamos, con guarda para que un `null` viejo del ring
   no mate un turno recién lanzado. Un run vivo que no arrancamos nosotros se adopta
   (barra + Detener) sin sondear, porque el streaming llega igual por el hub.
4. **Red de seguridad**: el orphan watch sigue. Con hub usa un tick de 30 s que consulta
   `session/info` (`hubOrphanTick`, `app.js:2018`), nunca `steer`, y libera la consola a los
   ~90 s de confirmarse que no hay run. El camino viejo quedó factorizado intacto
   (`orphanTickLegacy`, `app.js:1538`, 15 s + doble sonda con gracia).
5. `session/prompt` sigue cerrando el turno con su response, pero un `activeRunId=null` por
   evento lo cierra igual si el response se perdió (reload, socket caído).
6. **Compatibilidad**: con `hubWatch` en false/undefined nada cambia (soft-poll, sondeo por
   `steer`, orphan watch de 15 s, hot watch y `checkAdoptedRun` quedan como estaban).
