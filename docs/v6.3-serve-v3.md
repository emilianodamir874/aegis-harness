## 1. Robustez: runs que morian en silencio (punto 1)

### Diagnostico
- El run vive en `ActiveRunRegistry` (`crates/aegis/src/execution/active_run.rs`), creado por `start_prompt_run`
  y sacado por `clear_active_run` (acp/server.rs) o por `ActiveRunDropGuard::drop`.
- Los resultados de herramientas NO viajan por un canal propio: la tool se espera inline en el event loop del
  agente y los eventos llegan por `mpsc::UnboundedSender<AgentEvent>` -> `forward_agent_stream` (acp/server.rs).
- No habia NINGUN timeout de run (ni de stream de proveedor: solo los 600 s de HTTP).
- Superficie de muerte silenciosa (ordenada): (1) `machine.rs` cancela el step y los effects nunca se aplican
  (el resultado de la tool no se persiste); (2) `forward_agent_stream` con `if cancel_token.is_cancelled() { continue; }`
  descarta los eventos posteriores y termina como `Ok(Cancelled)` sin error ni tool updates -> **esto explica el caso
  observado** (tool completa, 2 tarjetas colgadas, UI muda); (3) `Emitter::emit` traga el fallo de envio;
  (4) `client_cx`/connection send, etc.

### Mitigacion implementada
- `ActiveRun` lleva ahora `last_progress_ms: Arc<AtomicU64>`, `stalled: Arc<AtomicBool>`,
  `client_cancelled: Arc<AtomicBool>` + helpers (`touch_progress`, `progress_age_secs`, `mark_stalled`,
  `was_stalled`, `mark_client_cancelled`, `was_client_cancelled`).
- `forward_agent_stream` marca progreso en **cada** evento recibido (chunks, tool call, tool result, usage).
- `on_prompt` lanza `spawn_run_watchdog(...)` por run: cada `AEGIS_RUN_WATCHDOG_POLL_SECS` mira la edad del
  progreso; si supera `AEGIS_RUN_STALL_TIMEOUT_SECS` y el run sigue vivo, hace, en este orden:
  emite un chunk de error VISIBLE al cliente -> `activeRunId = null` -> cancela el token del run.
  (Emitir antes de cancelar es a proposito: cancelar primero reentra en el camino silencioso.)
- `on_cancel` marca la cancelacion como pedida por el cliente. Al cerrar el turno, si fue cancelado y NO lo
  pidio el cliente y NO lo cerro el watchdog, se emite un aviso visible ("El turno se interrumpio de forma
  inesperada..."). Es el caso "se cayo la conexion / cancelacion interna" que antes era 100% mudo.

### Knobs
- `AEGIS_RUN_STALL_TIMEOUT_SECS` (default 900 = 15 min; 0 desactiva el watchdog).
- `AEGIS_RUN_WATCHDOG_POLL_SECS` (default 30, minimo 5).
Nota: el timeout de shell es 300 s, asi que 900 s no da falsos positivos en tools normales.

## 2. Herramientas: cap de salidas (punto 4)

### Efecto real verificado (no asumido)
- `AEGIS_MAX_TOOL_RESPONSE_SIZE` se lee en `crates/aegis/src/agents/large_response_handler.rs`
  (`max_tool_response_size()`), default **200.000 CHARs** (no bytes). El valor del usuario (60000) aplica.
- El cap SOLO mira `content.as_text()`. Un bloque de texto por encima del umbral se reemplaza por un puntero
  ("The response returned from the tool call was larger (...) and is stored in the file ...") escrito a un
  tempfile `aegis_mcp_response_*.txt`; ademas hay una segunda pasada que junta varios bloques de UN
  `CallToolResult`.
- **Las imagenes nunca pasaban por el cap** (`None => pass through`). Ese es el agujero real.
- Medido en la DB (`sessions.db`): 137 mensajes >60k chars, TODOS rol `user`, **54,6 MB de datos de imagen**;
  el mayor = 2,3 MB en un solo mensaje (toolResponse con imagen de 1,6 MB). El texto de assistant topea en 78 KB
  => el cap de texto esta funcionando; lo que se acumulaba sin freno eran las imagenes de `read_image`.

### Cambio implementado
- `process_tool_response` ahora tambien mira las imagenes: si `image.data.len()` (base64) supera el umbral,
  decodifica y escribe el archivo con extension segun MIME (`aegis_mcp_image_*.png|jpg|...`) y deja un puntero.
- Knob: `AEGIS_MAX_TOOL_IMAGE_BASE64_SIZE` (default 1.500.000 chars base64 ~ 1,1 MB decodificados; 0 desactiva).
  Trade-off explicito: la imagen derramada deja de ser visible para el modelo; el archivo queda para
  redimensionar/leer de nuevo.

### Evidencia medida
- 6/6 tests unitarios nuevos pasan (`cargo test -p aegis --lib ... large_response`), incluido
  `oversized_image_is_spilled_to_a_file` (1,2 MB -> archivo + puntero .png) y el mixto texto+imagen.
- `cargo check` de la lib con el set CI: limpio (solo warnings preexistentes).

### 2. Steer aceptada y NO consumida es lo que se reenvia

- **Persistido != consumido.** `discard_pending_steers` (`aegis/src/agents/agent.rs:334`) vacia la
  cola sin devolver nada, y `clear_active_run` (`acp/server.rs:1994-2001`) la llama al cerrar el
  run: la indicacion aceptada queda TIRADA pero su mensaje ya esta persistido. `finishSettle` lo
  daba por "recibida por el agente" solo porque el texto estaba en el historial
  (`textInServerHistory`), asi que no la reenviaba y quedaba muda.
- **Fix (cliente, sin cambio de protocolo)**: el server YA publica la indicacion encolada sin
  consumir en `_meta.aegis.queuedSteer`. Ahora, cuando eso llega, la steer se marca
  `serverQueued = true`; y en `finishSettle` el historial ya NO alcanza como prueba de consumo si
  el server la tenia encolada -> la indicacion vuelve a la cola y se reenvia como mensaje.
- Caso de origen: sesion `20261012_36`, "vos podes sacar screenshots" (17:27:57).
- **Recomendacion servidor (NO hecha)**: que `discard_pending_steers` devuelva los ids que tira y
  que `clear_active_run` los emita en el meta aegis. Asi el cliente deja de inferir y sabe.

## BUG CRÍTICO CONFIRMADO: recargar la página MATA el turno en curso (Ctrl+F5)

**Síntoma que reportó Emiliano**: al refrescar se pierde el streaming "y creo que incluso se
detienen los turnos". Verificado: **se detienen**.

### Evidencia (medida, no inferida)

Sesiones de test `20261012_53` y `_54` (turno lanzado desde el navegador, tool de 25 s, reload a
los 6 s). Lo que quedó persistido en `sessions.db`:

```
user      >> "Usá execute_typescript con: await new Promise(r => setTimeout(r, 25000))..."
user      >> <turn-context>
assistant >> [{"type":"thinking","thinking":"The user wants me to run execute_typescript with..."}]
```

Ni `toolRequest`, ni `toolResponse`, ni respuesta final. **El turno muere justo después del
thinking**, en el instante de la recarga. El mismo prompt SIN recargar completa normalmente
(medido: título generado + tool + respuesta).

Del lado del cliente, tras el reload y antes del arreglo (`ui/desktop/scripts/goose-web-reload3.mjs`):

```
watchDbg: ticks: 0        <- el watcher de turno adoptado NUNCA arranca
          interrupted: 1  <- y la carta pendiente queda marcada como interrumpida
```

### Mecanismo (código)

- `server.rs:2357`: `on_prompt` crea `let _run_guard = ActiveRunDropGuard { ... }`.
- `server.rs:257-259`: `impl Drop for ActiveRunDropGuard` → **`self.cancel_token.cancel()`**.
- El guard vive en el scope del handler de `on_prompt`, cuya task pertenece a **la conexión**. Al
  cerrarse el WebSocket, esa task/futuro se dropea → el guard se dropea → **el run se cancela**.
- Además el stream de eventos está atado al `cx` capturado al lanzar el prompt
  (`forward_agent_stream`), que ya está muerto; los envíos fallidos se tragan
  (`Emitter::emit`), así que la conexión nueva no recibe nada.

Es la misma familia del punto 1 de la ronda (muertes silenciosas del run), pero con un disparador
distinto: no un stall del proveedor, sino el cierre de la conexión.

### Mitigación aplicada HOY (cliente, sin Rust) — mejora parcial, no cura

En `checkAdoptedRun` (app.js) se agregó un camino de recuperación por **actividad de la sesión**:
si el probe del run no lo ve desde una conexión nueva pero la sesión estuvo activa hace <150 s,
se asume que el turno sigue, **no se barren las cartas**, se muestra la barra y se refresca la
conversación cada 2,5 s hasta que la sesión se enfría (`startHotWatch`/`hotTick`).

Medido antes → después del mismo test de reload:

| | antes | después |
|---|---|---|
| watcher adoptado | `ticks 0` (no arranca) | `adopted: true` |
| carta marcada interrumpida | `interrupted: 1` | `interrupted: 0` |
| refrescos efectivos | 0 | `softResyncs 5 → 32` |
| barra de turno tras F5 | ausente | presente hasta que la sesión se enfría |

Ojo: el refresco pasa a ser **incondicional** porque el `messageCount` que ve una conexión que no
es dueña del run **viene congelado** (ya estaba documentado en el código).

**Lo que esta mitigación NO arregla**: el texto final, porque el turno ya murió en el servidor. Con
el fix de servidor abajo, este refresco es exactamente lo que hace aparecer el contenido.

### Fix de fondo (Rust, pendiente — requiere rebuild del serve)

1. **Desacoplar el run de la conexión**: ejecutar el cuerpo de `on_prompt` en una task propia
   (`tokio::spawn`) y que el guard viva ahí, de modo que el cierre del socket no lo dropee. El
   `cancel_token` ya es explícito (lo usa `on_cancel`), así que `Detener` sigue funcionando.
2. **Sink de eventos por sesión**: que `forward_agent_stream` resuelva el destino por sesión (el
   último conexión conectada a esa sesión) en vez de capturar el `cx` al lanzar el prompt. Con eso,
   al volver a la pestaña, el streaming **se reanuda** en vivo en vez de depender del refresco.
3. Verificación: el mismo `goose-web-reload3.mjs` debe mostrar la respuesta final apareciendo sola,
   y la DB debe avanzar hasta el `toolResponse` + texto final.

### Fix que falta (diseno, con el bloqueante identificado)

Hay que **desacoplar el run de la conexion**: ejecutar desde `let stream = agent.reply(...)`
(server.rs:2408) hasta el armado del `PromptResponse` (2461) dentro de un `tokio::spawn`, y que
`on_prompt` espere el `JoinHandle`. El `cancel_token` ya es explicito, asi que `Detener` seguiria
funcionando; el watchdog tambien.

**Bloqueante tecnico**: los handlers reciben `&self` (`async fn on_prompt(&self, ...)`,
server.rs:2337, dentro del `impl AegisAcpAgent` de la linea 1865), y para un `spawn` hace falta un
`Arc<AegisAcpAgent>` o equivalent. El `Arc` existe (el runner lo tiene: server.rs:2743
`pub agent: Arc<AegisAcpAgent>`) pero no es alcanzable desde `&self`. Opciones:
1. cambiar el trait/impl del handler para que sea sobre `Arc<AegisAcpAgent>` (asi `self.clone()` da
   el `Arc`) — probablemente via la macro de `aegis-acp-macros`;
2. o extraer el tramo a una funcion libre que reciba solo los `Arc` que necesita
   (`active_runs`, `agent`, `cx`) en vez de `&self`, moviendo dentro las llamadas a
   `forward_agent_stream` / `clear_active_run` / `send_session_usage_updates`.

La opcion 2 es mas contenida y no toca el codigo generado por la macro. **No se hizo** por riesgo:
es el camino critico de TODOS los prompts y un error de concurrencia ahi rompe el producto; requiere
una sesion de trabajo propia con el test de recarga como red de seguridad.
